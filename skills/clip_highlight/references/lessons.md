# clip_highlight 踩坑记录

> 记录构建「日语直播字幕 → 中文字幕 + 高光切片分析」流水线过程中，用 `test.srt`（1282 条 cue / 2h04m，`gemini-3.5-flash-lite`）实测得出的结论。
> 每条都附实测数据，不是经验之谈。

---

## 一、架构层

### 1. 副产品没有质量契约，别指望它

最初翻译是分析 prompt 的副产品 —— Task 段只规定了「模块一/模块二」，那段 `### 全文翻译` 是 Language Protocol「先翻译再分析」被理解成打印出来的草稿纸。

实测覆盖率：

| | 原始 cue | 翻译块 | 覆盖率 |
|---|---|---|---|
| Part-1 | 641 | 627 | 98% |
| Part-2 | 641 | 308 | **48%** |
| 合计 | 1282 | 935 | 73% |

**结论**：需要什么就把它定义成正式交付物、给它独立的一步。拆出独立翻译 pass 后覆盖率从 73% → **100%**。

### 2. 会话累积会拖垮后续轮次

Part-1 与 Part-2 唯一的差别是：Part-2 通过 `previous_interaction_id` 带着 Part-1 那 2500 行完整输出。结果 98% vs 48%。

翻译 pass 改成每批独立调用（`session_id` 恒为 `None`），术语一致性交给知识库保证（每批都带，约 2230 token），覆盖率 100%。

**副作用是好的**：批次独立意味着将来可以直接丢线程池并行，不用改结构。

### 3. 长输出会渐进降质，不是硬截断

Part-2 不是结尾被砍掉（翻到 01:59:58，全片 02:04:29），而是**中间越来越稀**：

```
01:05–01:23   几乎逐秒覆盖
01:13:36 → 01:16:10   断 2 分 34 秒
01:23:39 → 01:25:36   断 1 分 57 秒
01:44:51 → 01:49:17   断 4 分 26 秒
```

**结论**：控制单轮输出长度比控制输入长度更重要。删掉翻译要求后，分析单轮输出只剩约 40 行，耗时从 **2m47s → 24s**。

### 4. 别让时间轴经过 LLM

模型生成时间戳时实测产出：

```
01:07:10 -> 01:19:32     结束比开始晚 12 分钟
01:39:38 -> 01:40:43     之后接 01:40:13，乱序重叠
01:59:51 -> 01:59:51     零时长
```

改成「译文按编号回填、时间戳直接取自源文件」后，产物时间轴与源文件**逐字节相同**。

**结论**：能用确定性代码做的，不要交给模型。时间戳损坏从「需要检测和修复」变成「结构上不可能发生」。

## 二、Prompt 层

### 5. 编号是最高杠杆的机制

让输出带编号（`<n> 译文`），带来三件事：缺失**可检测**、缺失**可定位**、缺失**可只重发那几条**。

实测价值：某次 Part-3 首轮缺了 **145/184** 条（明显被截断），补翻一轮全部救回，最终仍是 100%。没有编号的话这 145 条只会静默消失。

### 6. 每批编号从 1 开始，不用全局编号

小而一致的编号模型抄得更准，四位数编号容易漂；而且每批结构完全一致。全局位置由脚本按批次偏移换算。

（`split_srt` 早就因为同样的理由给每个分片重新编号。）

### 7. 逐行解析，不要整体解析

`<n> 译文` 一行一条，用 `^\s*<(\d+)>\s*(.+?)\s*$` 逐行抽取：

- 某一行写坏 → 只丢那一条
- 输出被截断 → 已输出的部分仍全部可用
- 模型擅自加了 ` ``` ` 代码块或「好的，以下是翻译：」→ 自动被忽略

实测这三种情况都验证过。JSON 相反 —— 一个未转义的引号或一次截断，整批 parse 不出来。

### 8. ⚠️ 给模型边界值会诱导它锚定

为了防止时间戳越界，曾在 prompt 里注入 `【本片时间范围】00:00:28 - 01:05:05`。结果**变得更糟**：

```
[00:00:28 - 01:05:05]   ← 一条覆盖整个分片
[01:05:05 - 01:21:47]   ← 把范围终点当成起点往后外推
[01:43:40 - 02:05:05]
```

移除后恢复正常：17 条首尾相接、完整覆盖到 02:04:32、零越界。

**结论**：约束模型抄写时，让它**照抄输入**比告诉它**上下限**可靠。给出的具体数值会成为它复用的锚点。

### 9. 减少输入里的歧义源，比加规则有效

带毫秒的时间轴 `00:13:36,040` 被读成 `13:36:04`（把毫秒当秒段），同一份输出里还混用两种格式。

在拼接分析输入时把 `,mmm` 剥掉 → 时间戳格式问题**完全消失**，无需任何 prompt 规则。

### 10. 正向规则，不要负向黑名单

知识库禁的是「阿卡西**娅**」，模型写的是「阿卡西**亚**」—— 同音不同字，黑名单漏掉。

规则要写成「只能输出 `Acacia`」而不是「禁止写成阿卡西娅」。

### 11. 规则有歧义时，模型会选错分类

原来的保留项规则把两类混在一句话里，模型把「括号注原文」的模式套到了必须原样保留的专名上，产出 `阿卡西亚（Acacia）`。

拆成甲类（原样保留，前后不得有中文）/ 乙类（中文 + 括号注原文），并写明判断顺序后：

```
之前:  Acacia ×9  +  阿卡西亚（Acacia）×4
之后:  Acacia ×9  +  音译 ×0
```

### 12. 上游缺陷会被下游忠实继承

「阿卡西亚」出现在分析产物里，第一反应是改分析 prompt —— 但 grep 一下发现它来自**翻译产物**（`test.zh.srt` 有 3 处），分析只是忠实转述。

**结论**：多步流水线里发现质量问题，先 grep 上一步的产物再动手，否则是在治症状。

## 三、工程层

### 13. 机械校验能抓出人肉发现不了的问题

两处校验都立过功：

- 翻译的覆盖率报告 → 让 100% 这件事可验证，而不是「看起来挺全」
- 分析的时间戳越界校验 → 当场抓出第 8 条那次回归（`7 timestamp(s) outside ...`）

否则只会看到「跑完了」，然后交付一份坏数据。

### 14. 限流不是瓶颈，失败代价才是

实测账号限额 RPM=15 / TPM=2.5M / RPD=500，而实际负载：

| | 值 | 限额 | 余量 |
|---|---|---|---|
| 请求速率 | 约 1.3 RPM | 15 | 10× |
| token 速率 | 约 15k/min | 2.5M | 160× |

串行跑永远撞不到。真正的风险是**一次失败丢掉全部进度**（写文件在最后）。

**解法是增量落盘，不是主动限流**：每个分片翻完立刻写进 `tmp/translated_srts/`，重跑自动跳过已完成的。`call_llm` 的 429/5xx 退避扛瞬时故障，落盘扛退避也救不回来的情况。

### 15. thought token 占 90%+ 且无法预估

一次最小探测（输入 9 token）的 `usage`：

```
total_tokens          349
├─ total_input_tokens          9
├─ total_output_tokens        15
└─ total_thought_tokens      325   ← 93%
```

**结论**：本地记账算不准配额，别费劲做主动限流。响应头里也没有任何 `x-ratelimit-*` 或 `retry-after`（查过）。

### 16. 分片阈值：等分优于固定

`split_srt` 是「上限语义」——`ceil` 算份数再 `ceil` 算每份大小。1282 条按 200 切得到 `6×184 + 178`，而固定切法会得到 `6×200 + 82`。

那个 82 条的尾片丢给 LLM 基本是废的（没上下文、没法判断）。等分不产生畸形分片，份数还完全一样。

### 17. 环境相关

- **Windows cp936/cp950**：字幕含日语，`print` 会直接抛 `UnicodeEncodeError`。所有入口都要 `configure_utf8_stdio()`。
- **utf-8-sig**：Whisper 产出的 SRT 常带 BOM，用普通 utf-8 读，第一个块序号会变成 `﻿1`。`utf-8-sig` 读普通 UTF-8 结果完全相同，无脑用它。
- **CRLF**：`Path.write_text` 在 Windows 上会转换换行，grep 时不要用 `$` 锚定行尾 —— 排查时曾因此得到 0 匹配的假结果。
- **ASR 幻觉**：静音段会产出重复的 `ご視聴ありがとうございました。`（test.srt 的 cue 1-3 和最后一条都是）。不要在翻译阶段过滤 —— 会破坏编号对应，应该在 ASR 那一侧处理。
